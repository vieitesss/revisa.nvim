REQUIREMENTS                                               *revisa-requirements*

Neovim 0.10 or newer. No other plugins are required.

The plugin uses the revisa CLI. It looks for an executable named revisa on PATH,
then for bin/revisa inside the plugin directory. If neither exists, an error
names both locations. The CLI is the only code that reads or writes comments.

The Rex features, |:Revisa-beside| and |:Revisa-send| with notify = "rex",
need REX_SESSION set and rex on PATH. Otherwise they report that and do
nothing.

The worktree picker uses |vim.ui.select|. It needs no picker plugin.

COMMANDS                                                      *revisa-commands*

:Revisa comment                                               *:Revisa-comment*
    Write a new-side comment on the current line of a saved, real file buffer.

:[range]Revisa comment
    Write a comment on all lines in [range]. For a visual selection: >

        :'<,'>Revisa comment
<
    Anchor text contains every selected line, read from the file on disk.

    Modified buffers are refused with "save the buffer before commenting".
    Virtual buffers, patch buffers with a nonempty 'buftype', scheme:// names,
    and buffers without a real file on disk are refused without storing a
    comment. Another diff tool's real file buffer works without an adapter,
    but its old-side buffer does not: commenting there is refused with
    "revisa: cannot comment in a fugitive:// buffer; open the file or use
    :Revisa review", naming that tool's scheme.

    In the diff view of |:Revisa-review|, the left side comments on the old
    side: the comment belongs to the branch under review and is read at the
    base commit. A line only the base has, such as one the change deleted,
    takes a comment there. A renamed entry reads its old path, so comment on
    that path stores the old path. The right side of a deleted file stores
    nothing and reports that the path is not found in the worktree.

:Revisa refresh                                               *:Revisa-refresh*
    Reload comments for the current file.

:Revisa resolved                                             *:Revisa-resolved*
    Show or hide resolved comments, in every loaded buffer that has revisa
    marks. They are hidden by default. A shown resolved comment prints its
    reply below its body, so you can judge the fix. From Lua, the same
    toggle is require("revisa").toggle_resolved().

:Revisa review [WORKTREE]                                     *:Revisa-review*
    List the session changes of a worktree. Without [WORKTREE], pick one
    with |vim.ui.select|, labelled with its branch and path. [WORKTREE] is
    a worktree path or a branch; it skips the picker and works from any
    worktree of the project.

    The list opens in a new split, in a scratch buffer named
    revisa://changes/<branch>. A detached worktree has no branch, so its
    buffer is named revisa://changes/detached-<sha7>-<worktree name>, and
    two detached worktrees never share a buffer. Its header shows the
    worktree path, the branch and the base: the merge-base with the
    project's default branch, or the worktree's HEAD when it is on that
    branch. Each entry is one line, a status then a path, with old -> new
    after a rename: >

        worktree /repo/linked
        branch feat/x
        base 3f9c2e1 (main)

        M src/a.lua
        ? notes.txt
        R src/old.lua -> src/new.lua
<
    Status is M, A, D, R, or ? for a file git does not track yet.

    <CR>        Open the change in a diff view, in a new tab. Details
                below.
    o           Open the file in that worktree, in the previous window,
                alone. Comments on it appear as on any other real file
                buffer. A deleted entry is reported instead of opening a
                path that is not there.
    R           Reload the list from the CLI.
    q           Close the list.

    The diff view puts the base content on the left and the worktree file
    on the right, with 'diff' set in both windows. The left side is a
    read-only scratch buffer named revisa://<base sha7>/<path>, filled by
    git show of the base commit and given the filetype of the path, and
    its old-side comments are drawn as it opens. A renamed entry reads
    its old path there; an added or untracked entry has an empty left
    side.

    The right side is the real file, so it stays editable and comments
    work there as on any other real file buffer. A deleted entry has an
    empty read-only revisa://deleted/<path> on the right, and commenting
    there is refused like in any other virtual buffer.

    Revisa computes no diff: it reads the left side with git and lets
    Neovim render the comparison. A file with a NUL byte in the first
    8000 bytes of either side is reported as "revisa: <path> is binary"
    and does not open. q on the left side closes the diff tab.

    The CLI of a review runs in the worktree of the current buffer's
    review target, so :Revisa review works from any buffer of the project
    even when Neovim's working directory is outside it. An explicit
    [WORKTREE] only picks the worktree to list; it does not change where
    the CLI runs.

    The keys are buffer-local. require("revisa").review(worktree) does the
    same as the command.

:Revisa beside [WORKTREE]                                   *:Revisa-beside*
    Open the review in a new split beside an agent pane, through Rex. It
    needs REX_SESSION set and rex on PATH; without either, it reports
    "revisa: rex needs REX_SESSION set and rex on PATH" and opens
    nothing.

    Without [WORKTREE], pick a worktree with |vim.ui.select|, as for
    |:Revisa-review|. [WORKTREE] is a worktree path, and naming it skips
    that picker.

    Then every pane of the Rex session is offered with |vim.ui.select|,
    except the one Neovim runs in. Each entry shows the block id, the pane
    label and the directory of the pane's program. The one pane whose
    program works in the chosen worktree is offered first, marked as the
    match. The pick is always explicit.

    The picked pane is split to the right. The new pane runs
    "nvim +Revisa review <worktree>" with its working directory set to
    that worktree, so the review opens where the agent works.

    Block ids are read from rex block ls --json on every call and never
    stored: they expire with the pane. No key is mapped.

    require("revisa").beside(worktree) does the same as the command.

:Revisa send [WORKTREE]                                         *:Revisa-send*
    Tell an agent that comments are waiting on a branch. It needs
    notify = "recado" or notify = "rex" in |revisa-setup|. Without it the
    command says which settings it needs; a notifier that is not
    available reports why and sends nothing.

    [WORKTREE] is a path or a branch, as for |:Revisa-review|. Without it
    the worktree is the changes buffer's, the diff view's, or the current
    file's git worktree. The branch of that worktree goes in the message.

    With notify = "recado", only live agents on this machine are offered:
    remote agents, and Codex, which cannot receive these messages, are
    dropped. The one agent whose working directory resolves to a worktree
    root equal to the worktree's is offered first, marked as the match.
    No match, several matches or an unknown working directory means no
    preselection. OpenCode's reported working directory is not used.

    With notify = "rex", every pane of the Rex session is offered, except
    the one Neovim runs in, and the one whose program works in the
    worktree comes first, marked as the match. The pane is captured with
    rex capture before the confirm, which shows the last 10 lines it
    holds. The pick is always explicit, and the confirm sends to that one
    pane. Rex types into whatever runs there: if the agent has exited,
    the text goes to the shell.

    |vim.ui.select| always asks, and cancelling sends nothing.

    The message carries no comment content, only where to read it: >

        revisa: review comments are waiting on branch 'feat/x'. Run:
        revisa list --branch 'feat/x' --status open. Answer each with
        revisa resolve, not recado reply.
<
    The branch is one line in the message and single-quoted for a shell,
    with an embedded quote escaped. Revisa never reads recado inbox and
    never registers an agent.

    Through recado, the send sets RECADO_ADDR=revisa in the child process
    only, keeps the default message kind and adds --meta
    revisa_branch=<branch>. Exit 0 reports "revisa: sent to <id>" and
    returns without polling. Exit 1 reports the CLI failure from recado's
    stderr. Exit 2 opens the picker again.

    Through rex, the message is typed with rex send and Return is pressed
    with rex send-key, both into the picked block. Success reports
    "revisa: sent to <block>" and returns; a failure reports rex's stderr.

Comments also refresh on BufReadPost of real file buffers and after a successful
add. Switching to an already loaded buffer does not refresh comments.

CLI failures are shown through vim.notify at ERROR level, using the CLI's
stderr. For example, a detached HEAD is reported rather than guessing a branch.

==============================================================================
COMMENT EDITOR                                                  *revisa-editor*

The editor is a multiline floating buffer below the last selected line.
Empty virtual lines reserve space in the file window; the float occupies that
space and does not cover file lines. The file window may scroll to make room.

The float has no border, is at most 60 columns wide, and is four rows tall
(or shorter when the file window is small). Edit it like a normal buffer.
Longer bodies can be entered by scrolling inside the editor.

    :w          Save the comment.
    <C-s>       Save in normal or insert mode.
    q           Cancel in normal mode.

Canceling or saving an empty/whitespace-only body stores nothing. A successful
save, empty save, or cancel closes the editor and removes its reserved space.
A failed save keeps the editor, body, and reserved space intact so you can retry
or cancel. Saving also refuses file-buffer edits made while the editor was open.

MAPPINGS                                                      *revisa-mappings*

<Plug>(revisa-comment)                                  *<Plug>(revisa-comment)*
    Normal mode: comment on the current line.
    Visual mode: comment on the selected line range.

There are no default keymaps. Example user mappings: >

    vim.keymap.set("n", "<leader>rc", "<Plug>(revisa-comment)")
    vim.keymap.set("x", "<leader>rc", "<Plug>(revisa-comment)")
    vim.keymap.set("n", "<leader>rr", "<cmd>Revisa review<cr>")
<
The changes buffer adds its own buffer-local <CR>, o, R and q keys.

DISPLAY                                                        *revisa-display*

Open new-side comments for the file appear inline:
    - A > sign on every line of the comment's range.
    - The full body as virtual lines below the last line.

Resolved new-side comments are hidden by default. With :Revisa resolved they
appear inline too:
    - A ✓ sign on every line of the comment's range.
    - The full body, then the reply, as virtual lines below the last line.
      The first reply line starts with "reply: ".

A comment the CLI reports as outdated or unknown has no current lines to
draw on: an outdated one's anchor text is gone, an unknown one's branch is.
It is not drawn on a guessed line. Instead one block of virtual lines is
drawn below the last line, grouped by condition, with one empty line
between groups. Each group starts with its heading and holds each
comment's body and was: lines: >

    outdated (2)
    Handle nil here
    was: local x = y
    was: if x then
    Another body
    was: run(x)
<
A group of unknown comments reads the same, headed "unknown (1)" and using
RevisaUnknown. While the block is not empty, the first line shows a
right-aligned summary in RevisaOutdated: >

    revisa: 2 outdated, 1 unknown
<
A zero count is omitted. The block is virtual: it changes no buffer line
and is not written by :write. |:Revisa-refresh| redraws it, and when the
anchor text comes back the comment returns to its line with no marker. The
empty new side of a deleted file in the diff view shows the same block.

Old-side comments are drawn on the old side of the diff view, when the diff
opens and again after a comment is added there. A new-side buffer never
shows them. The base commit pins them: when the base has moved, as after a
rebase, the diff's old side is another commit and none of them are drawn.
`revisa list` still prints such a comment, with its side and short
commit, and it is never reported as outdated.

Highlight groups use default links, which users can override:

    RevisaSign          DiagnosticSignInfo                       *RevisaSign*
    RevisaComment       Comment                                  *RevisaComment*
    RevisaResolved      DiagnosticSignOk                     *RevisaResolved*
    RevisaReply         DiagnosticOk                            *RevisaReply*
    RevisaOutdated      DiagnosticWarn                     *RevisaOutdated*
    RevisaUnknown       DiagnosticError                     *RevisaUnknown*
    RevisaWas           Comment                                 *RevisaWas*

PROJECTS                                                      *revisa-projects*

Inside git, the buffer's file path determines the worktree and project root.
The CLI runs in that worktree and infers its branch. The comment path is
relative to the git top level, not Neovim's working directory.

Comments belong to a branch, not a worktree path. The same file in another
worktree of that branch reads the same comments through the CLI.

Outside git, the CLI runs in Neovim's current working directory when the file
is under it, otherwise in the file's own directory. The project root is the
nearest ancestor of that run directory containing a .revisa/ directory, or the
run directory itself when no store exists. Comment paths are relative to that
root. The plugin never creates or opens the store directly.

==============================================================================
SESSION CHANGES                                                *revisa-changes*

Session changes are everything that differs between a worktree and the base:
its commits since it left the default branch, uncommitted edits to tracked
files, deletions, renames, and files git does not track yet.

:Revisa review reads them through the CLI, so the same data is available
there. The shell command opens Neovim straight in the review, keeping the
working directory: >

    revisa review             pick a worktree
    revisa review feat/x      a branch, or a worktree path
    revisa review ../linked
<
REVISA_NVIM chooses the editor executable instead of nvim.

The CLI prints the same data for scripts and agents: >

    revisa worktrees [--json]
    revisa changes [--worktree PATH|BRANCH] [--json]
<
The default branch is refs/remotes/origin/HEAD, then init.defaultBranch,
then main, then master. If none of them exists, changes fails and names
what it tried.

On the default branch the base is HEAD, so only uncommitted work is listed:
sessions commit to their own branch.

==============================================================================
SETUP                                                            *revisa-setup*

No setup call is required. plugin/revisa.lua registers the command, mappings,
autocommand, and highlight groups when the plugin loads.

For configurations that expect a setup function, this is supported: >

    require("revisa").setup({ notify = "recado" })
<
The only option is notify, which chooses how |:Revisa-send| reaches an
agent: >

    "none"      Do not notify agents. The default.
    "recado"    Send through recado, which must be on PATH.
    "rex"       Type the message into a Rex pane, which needs REX_SESSION
                set and rex on PATH.
<
Any other value is an error naming these three. Without a setup call the
setting stays "none".
